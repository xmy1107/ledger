# 项目规划

## 产品定位

把亲密关系中的事件、金钱、承诺、情绪、修复行为和双方叙述沉淀成可追踪账本。AI 不直接替代法律或心理咨询判断，而是先做结构化拆解：事实、主张、需求、风险、可追问问题和暂定公平倾向。

## MVP 边界

当前版本只解决三件事：

- 像记账一样录入一件关系事件。
- 保存金额、叙述者、正文、标签和关联事件，形成 DAG 雏形。
- 调用 Ollama 或本地规则给出简单分析，帮助下一次输入更客观。

## 技术选择

- 前端：原生 HTML/CSS/JS，先减少构建和部署成本。
- 后端：Python 标准库 HTTP 服务，后续可平滑迁移 FastAPI。
- 数据库：SQLite 起步，事件和边关系清晰；后续复杂图查询可迁移 PostgreSQL + Apache AGE、Neo4j 或 Kuzu。
- AI：`backend/ai.py` 统一封装，默认 Ollama `deepseek-r1`，失败后本地规则兜底。
- 记忆：`backend/memory.py` 统一封装，当前 SQLite 摘要，安装 `mem0ai` 后通过 `LEDGER_USE_MEM0=1` 启用 mem0。

## 数据模型

- `events`：单条事件，包含时间、叙述者、金额、情绪强度、正文、标签和 AI 分析。
- `event_edges`：事件之间的关联边，支持因果、重复模式、证据、反驳等后续关系类型。
- `memories`：事件摘要，作为长上下文压缩层和 mem0 fallback。

## AI 角色路线

1. 事件分析员：事实/主张/需求/风险拆分。
2. AI 判官：基于双方叙述和证据，输出可解释评分，而非一句话判输赢。
3. AI 心理师：分析依恋模式、沟通循环、边界和修复能力。
4. AI 调解师：生成双方都能接受的沟通脚本、协议和复盘问题。

## 双方输入机制

后续每个事件可以拥有两个以上叙述版本：

- 男方叙述。
- 女方叙述。
- 共同确认事实。
- AI 标注冲突点。
- 证据附件或微信片段引用。

AI 判官的 PK 进度条应拆成多个维度：事实可信度、承诺违背、金钱公平、情绪伤害、修复行为、长期模式。总分只能作为入口，不能遮蔽细节。

## 微信导入路线

1. 导入原始文本或 HTML 聊天记录。
2. 解析时间、发送方、消息文本、转账/红包关键词。
3. 按时间窗口聚合为候选事件。
4. 用户确认、合并或拆分事件。
5. 写入事件 DAG，并把原始消息作为证据引用。
